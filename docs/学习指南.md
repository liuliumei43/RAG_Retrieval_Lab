# 先理解一条完整请求

项目主线是“从文档找依据，再组织回答”。第一遍只看 PDF 解析、分块、检索和回答；RRF、重排、流式和会话可以在第二遍再学。

## 一、用自己的话说明用途

用户上传一份资料，再问资料中的问题。程序找到相关段落，把它们与问题一起交给模型，最后返回回答和原文页码。这里运行的是已有 embedding 和生成模型的推理，没有训练或微调模型。

## 二、上传 PDF 后发生什么

`/upload` 调用 `load_pdf`，得到文字及实际页码。`chunk_pages` 在每页内按约 500 个字符切块，相邻块重叠 50 个字符，再由 `embed_texts` 获得每块的向量。FAISS 保存向量，BM25 保存关键词统计，块本身保留文字和页码。

当前分块是固定字符窗口，不是按完整句子或模型 token 切分。页内分块让来源页码明确，但跨页句子和表格可能被拆开，这是一个实际限制。

## 三、提问后发生什么

1. 把问题转换为向量，寻找语义接近的块。
2. 用 BM25 寻找关键词匹配的块。
3. 用 RRF 合并两份排名。
4. 从候选中选出少量块；重排器只处理候选。
5. 程序组装“问题、检索内容、历史对话”，发送给生成模型。
6. API 返回答案，以及候选块的文字和页码。

## 四、每个选择为什么这样做

| 选择 | 可以这样解释 | 代价或限制 |
| --- | --- | --- |
| 分块 | 只发相关小段，减少无关上下文 | 可能拆开条件、表格或跨页内容 |
| 重叠 | 保留边界附近的一部分内容 | 重复内容增加，不能保证语义完整 |
| 向量检索 | 帮助找到不同措辞但意思相近的内容 | 精确编号、密集事实可能排序不理想 |
| BM25 | 补充编号、名称等关键词匹配 | 不擅长同义表达；英文分词对中文有限制 |
| RRF | 根据排名合并结果，免去硬凑两种分数尺度 | 排名靠前不等于一定正确 |
| 重排 | 更仔细比较问题和候选块 | 增加耗时，也可能降低某些问题的效果 |
| 返回页码 | 让用户能回到原文核对 | 检索来源存在不等于答案已验证 |

RRF 的直觉：在两份排名中都靠前的段落，会得到更多票。代码中每份列表给某个位置的分数是 `1 / (60 + 排名)`，排名从 1 开始。它与语义相似度、模型置信度是不同的量。

## 五、本版两个容易解释的修复

**PDF 读取。** 原实现把上传内容写到固定的临时文件名。两个上传交错时，可能相互覆盖。本版直接从 `BytesIO` 读取，减少共享文件状态；这没有解决整个单文档全局索引的并发问题。

**BM25 零分排名。** 如果问题的词在文档里完全没有命中，各段落都可能是零分。原实现仍给这些零分结果排顺序并参与 RRF，相当于给无关结果投票。本版只加入正分关键词结果；没有这样的结果时就使用原向量排名。这是排序修复，不是判断“文档是否有答案”的置信阈值。

## 六、怎样判断是否有效

基础回归测试检查程序行为，例如分块页码、零分排序、关键词补充、来源返回和会话传递。它们不需要下载模型，也不会调用收费 API。

真实质量评测需要固定 PDF、问题、模型配置，分别记录检索是否找到相关内容和最终回答是否正确。上游的 19 个问题依赖真实模型；本版没有把原作者报告的全通过结果当作自己的测试结果。只匹配答案关键词也可能漏掉错误，应结合原文人工复核。

## 七、逐步阅读

- 第一遍：`pdf_loader.py`、`rag.py`、`main.py` 的 `/upload` 和 `/query`。
- 第二遍：`store.py` 中两种检索及 RRF，`reranker.py` 的候选选择。
- 第三遍：对照 `test_core.py`，解释一次修复如何通过测试确认。

先能复述“输入什么、在哪里处理、输出什么”，再理解为什么这样设计。项目来源和本版实际修改需要一起说明；近期引入的学习项目不能描述成此前已长期完成的独立研发经历。

可以用于练习大模型应用中的资料检索、上下文构造、接口封装和评测思路。该仓库本身不包含医疗数据、医学模型训练或临床验证，不应把通用文档问答描述成已完成医疗 AI 系统。
